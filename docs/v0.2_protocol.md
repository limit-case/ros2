## 2. Data

- Held-out set: **all 52 scenes of the official TransCG test split**, as listed under the key `"test"` of the
  dataset's top-level `metadata.json` (shipped in `transcg-info.zip`; the same file lists the 78 `"train"` scenes).
  D435 views only (`depth1*.png`, `rgb1.png`, read with GlassBench `loader.load_transcg(view, "D435")`). The
  metadata counts 11766 D435 test samples.
- Sample: **all D435 views that have ground truth** in those scenes, no sub-sampling. Decision rule set by the
  owner: all views if the estimated full runtime is at most 4 hours, otherwise 5 views per scene with seed 20261112.
  Estimate, made on 10 views of TRAIN scene 1 before any test scene was touched: 0.47 s per view for both methods
  together, so about 1.5 hours for 11766 views (download and unzip time not counted). 1.5 h <= 4 h, so all views.
- Only scenes 1 to 10 are on the evaluation machine today. Of the test split that is scenes 5, 7 and 8. GlassBench has
  already measured raw-depth statistics on them (no filter, not this method). They are part of the full run and are
  not run early.
- No tuning, no subset selection after seeing results, no reruns except for a crash (then the same command again;
  finished scenes are skipped). The script prints no metric and no verdict until all 52 scenes are done.

## 3. Run, once, streaming

TransCG comes as 13 zips of 10 scenes each (13 to 16 GB per zip, about 192 GB in total) from
<https://graspnet.net/transcg>. The run never needs more than one zip plus one extracted scene on disk:

```bash
docker build -f docker/Dockerfile -t lc-cli:head .           # once, at the frozen commit: builds filter_cli
scripts/run_transcg_zip.sh ~/Downloads/transcg-data-2.zip    # repeat for every zip, in any order; delete the zip after
```

For each official test scene in the zip that is not done yet, the wrapper extracts that scene only, runs both
methods on it, saves the bucket counts (`out/transcg/transcg_d435_test/scenes/scene<N>.json`, numbers only), adds a
line to `done.log` and deletes the extracted scene. Scenes already extracted on the machine (5, 7, 8) are evaluated
in place and kept. Train scenes inside a zip are never extracted. `--dry-run` lists what a zip would do.

## 4. Declared before the run: what counts as confirmed

**PASS only if all three hold on the held-out set:**

1. wrong removed (RGB) >= 1.5 x wrong removed (v0.1), **and** the lower bound of the 95% bootstrap confidence
   interval of that ratio is >= 1.5;
2. correct lost (RGB) <= correct lost (v0.1) + 2.0 percentage points;
3. outside-mask flagged (RGB) < outside-mask flagged (v0.1).

Otherwise FAIL. If it fails, v0.2 reports that and the method is not shipped as the default.

- Bootstrap: 2000 resamples **over scenes** (not pixels, not views), with replacement, fixed seed 20261112; pooled
  metrics are recomputed on every resample; the interval is the 2.5th to 97.5th percentile.
- Reported whatever happens: point estimates and 95% intervals of wrong removed, correct lost and outside-mask
  flagged for both methods, and of the ratio; wrong among returned (raw -> after); mask IoU and area against the
  ground-truth mask; share of wrong pixels inside the proposal; share of missing pixels.
- Secondary only: the same intervals from a bootstrap over views. Views of one scene are not independent, so this
  interval is optimistic (too narrow). It is labelled so and **never decides PASS**.

Known threats, stated up front: the mask network never saw TransCG (other objects, other backgrounds), so mask
quality may dominate; TransCG scenes are tabletop scenes, still not doors or windows; ground truth comes from
object models and tracked poses, not from opaque twins.

## 6. Result (2026-11-14)

Run once at the frozen commit `c1219e7`, all 52 official test scenes, 11766 D435 views, tolerance 5%. Every number
is from `results/transcg_d435_test_summary.csv` (pooled values only). Intervals are the 95% bootstrap over scenes.

| Metric | RGB proposal | v0.1 depth-only |
|---|---|---|
| Wrong removed | 35.7% (31.9 to 40.0) | 28.6% (23.6 to 33.9) |
| Correct lost | 11.0% (8.2 to 13.6) | 4.5% (3.1 to 6.0) |
| Outside-mask flagged | 2.2% (1.7 to 2.6) | 2.4% (1.9 to 2.9) |
| Wrong among returned (raw -> after) | 13.9% -> 10.4% | 13.9% -> 10.8% |

Ratio of wrong removed, RGB / v0.1: **1.25** (1.06 to 1.48).

| Condition of section 4 | Outcome |
|---|---|
| 1. Ratio >= 1.5 and its lower bound >= 1.5 | **failed**: 1.25, lower bound 1.06 |
| 2. Correct lost (RGB) <= correct lost (v0.1) + 2.0 points | **failed**: 11.0% against 4.5% + 2.0 |
| 3. Outside-mask flagged (RGB) < outside-mask flagged (v0.1) | held: 2.2% against 2.4% |

**Verdict: FAIL.** As declared, the method is not shipped as the default.

Also reported, as promised in section 4:

- Proposal mask against the ground-truth mask: IoU 45.9%, area 99.3% of the ground-truth area.
- Share of the wrong pixels that lie inside the proposal: 73.2%.
- Raw depth on the transparent-mask pixels: 62.7% correct, 27.1% missing, 10.1% wrong; 100.0% of the wrong pixels
  read too far.

Reading: the mask is the right size but only half in the right place, so mask quality limits the method, which is
the first threat named in section 4. This is an interpretation; no experiment here separates the mask from the
depth check.
